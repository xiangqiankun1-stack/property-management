# 物业管理系统数据库字段说明

> 说明：所有业务表都统一包含以下 8 个公共字段，后文各表不再重复列出，仅列业务字段。

| 公共字段 | 类型 | 含义/作用 |
|---|---|---|
| `id` | BIGINT AUTO_INCREMENT | 主键，唯一标识一条记录，由数据库自增生成 |
| `create_time` | DATETIME | 记录创建时间，用于审计和排序 |
| `update_time` | DATETIME | 记录最后一次修改时间，用于审计和判断数据是否为最新 |
| `create_user` | BIGINT | 创建该记录的操作人ID（关联 `sys_user_info.id`） |
| `update_user` | BIGINT | 最后修改该记录的操作人ID（关联 `sys_user_info.id`） |
| `description` | VARCHAR(255) | 对该记录的补充描述，可选 |
| `remark` | VARCHAR(255) | 备注信息，供人工填写额外说明，可选 |
| `deleted` | INT DEFAULT 0 | 逻辑删除标记：0=未删除、1=已删除。业务上"删除"记录时并不物理删除数据行，而是将该字段置为1，所有查询需默认加上 `deleted = 0` 条件过滤，便于误删恢复和数据留痕 |

## 一、系统权限模块

### 1.1 `sys_permission_info` 权限信息表

| 字段 | 含义/作用 |
|---|---|
| `permission_code` | 权限编码，程序内部用于唯一标识某个权限点，一般全局唯一 |
| `permission_name` | 权限的中文名称，用于界面展示 |
| `permission_type` | 权限层级类型：1=目录（一级分组，不可点击）、2=菜单（可跳转的页面）、3=按钮（页面内的操作权限，如"新增""删除"） |
| `parent_id` | 父级权限ID，自关联到本表 `id`，用于构建树形菜单结构；顶级节点为 `NULL` |
| `permission_icon` | 菜单图标标识，前端渲染菜单时使用 |
| `permission_str` | 权限字符串，通常用于前后端接口鉴权（如 `sys:user:add`），按钮级权限常用 |
| `permission_component` | 前端路由组件地址，菜单类型权限跳转时加载对应的前端页面组件 |
| `sort` | 排序字段，控制同级菜单/按钮的显示顺序 |

### 1.2 `sys_role_info` 角色信息表

| 字段 | 含义/作用 |
|---|---|
| `role_code` | 角色编码，程序内部识别角色的唯一标识（如 `ADMIN`） |
| `role_name` | 角色的中文名称，用于界面展示（如"管理员"） |

### 1.3 `sys_role_permission` 角色权限关联表

| 字段 | 含义/作用 |
|---|---|
| `role_info_id` | 关联 `sys_role_info.id`，表示这条关联属于哪个角色 |
| `permission_info_id` | 关联 `sys_permission_info.id`，表示该角色被授予的具体权限 |

一个角色可对应多条记录（多个权限），一个权限也可被多个角色引用，实现角色与权限的多对多关系。

### 1.4 `sys_user_info` 用户信息表

> 注意：这里的"用户"指后台操作人员（管理员、维修工、客服），不是业主。

| 字段 | 含义/作用 |
|---|---|
| `user_name` | 登录账号，唯一，用于系统登录 |
| `password` | 登录密码（存储的应为加密/哈希后的值，不应明文存储） |
| `phone_number` | 联系电话，可用于短信验证、找回密码等 |
| `avatar_address` | 头像图片的存储地址（URL 或路径） |
| `full_name` | 真实姓名，界面展示用 |

### 1.5 `sys_user_role` 用户角色关联表

| 字段 | 含义/作用 |
|---|---|
| `user_info_id` | 关联 `sys_user_info.id`，表示该关联属于哪个用户 |
| `role_info_id` | 关联 `sys_role_info.id`，表示分配给该用户的角色 |

一个用户可拥有多个角色，一个角色也可分配给多个用户，实现 RBAC 权限模型。

## 二、基础信息模块

### 2.1 `community` 小区信息表

| 字段 | 含义/作用 |
|---|---|
| `community_name` | 小区名称 |
| `community_address` | 小区详细地址 |
| `area` | 小区占地面积（平方米），用于统计展示 |
| `total_buildings` | 小区内楼栋总数，一般由楼栋表数据同步或统计得出，冗余存储便于快速查询 |
| `developer` | 开发商名称 |
| `property_company` | 负责该小区的物业公司名称 |
| `contact_phone` | 小区物业服务联系电话 |
| `status` | 小区状态：1=正常使用、0=停用（如已拆迁、系统内测试数据禁用等） |

### 2.2 `building` 楼栋信息表

| 字段 | 含义/作用 |
|---|---|
| `community_id` | 关联 `community.id`，表示该楼栋所属的小区 |
| `building_name` | 楼栋名称/编号（如"1号楼"） |
| `total_floors` | 该楼栋总层数，用于生成房屋编号或校验楼层合法性 |
| `units_per_floor` | 每层的户数，用于批量生成房屋数据或做容量统计 |
| `status` | 楼栋状态：1=正常、0=停用 |

### 2.3 `house` 房屋信息表

| 字段 | 含义/作用 |
|---|---|
| `building_id` | 关联 `building.id`，表示该房屋所属的楼栋 |
| `house_number` | 房屋编号/门牌号（如"1-1-101"），对外展示和查找房屋的主要标识 |
| `floor` | 房屋所在楼层 |
| `unit_number` | 单元号（一栋楼可能分多个单元） |
| `area` | 房屋建筑面积（平方米），常用于物业费计算 |
| `house_type` | 户型描述（如"两室一厅"） |
| `status` | 房屋使用状态：0=空置、1=已入住（业主自住）、2=已出租 |

### 2.4 `owner` 业主信息表

| 字段 | 含义/作用 |
|---|---|
| `owner_name` | 业主/住户姓名 |
| `phone_number` | 联系电话，用于报修、通知等场景联系业主 |
| `id_card` | 身份证号，用于实名登记，敏感字段，实际系统中应加密存储 |
| `gender` | 性别：1=男、2=女 |
| `house_id` | 关联 `house.id`，表示该人员关联的房屋；允许为空，兼容尚未分配房屋的登记场景 |
| `relationship` | 与房屋的关系：业主本人/家属/租户，区分产权人和实际居住人 |
| `status` | 状态：1=正常、0=停用（如已过户、已退租） |

## 三、物业业务模块

### 3.1 `repair` 报修信息表

| 字段 | 含义/作用 |
|---|---|
| `repair_no` | 报修单号，全局唯一，用于对外展示和跟踪（如"RP20260201001"） |
| `owner_id` | 关联 `owner.id`，表示发起报修的业主 |
| `house_id` | 关联 `house.id`，表示报修涉及的房屋 |
| `repair_type` | 报修类型（水电/门窗/管道/公共设施等），用于分类统计和派单 |
| `repair_content` | 报修的详细问题描述 |
| `repair_images` | 报修现场图片地址，多张以逗号分隔，辅助维修人员了解现场情况 |
| `contact_phone` | 报修时预留的联系电话（可能与业主档案电话不同，如临时联系人） |
| `expected_time` | 业主期望的上门维修时间 |
| `status` | 报修单状态流转：0待处理→1已派单→2维修中→3已完成→4已评价→5已关闭 |

### 3.2 `repair_order` 派单信息表

| 字段 | 含义/作用 |
|---|---|
| `repair_id` | 关联 `repair.id`，表示该派单对应哪一条报修单 |
| `worker_id` | 关联 `sys_user_info.id`，表示被指派的维修人员 |
| `assign_time` | 派单（指派维修人员）的时间 |
| `accept_time` | 维修人员接单确认的时间 |
| `complete_time` | 维修完成的时间 |
| `result_desc` | 维修结果说明，记录处理过程和结果 |
| `status` | 派单状态：0待接单→1已接单→2维修中→3已完成→4已取消 |

一条报修单可能对应多条派单记录（如首次维修未解决需要重新派单）。

### 3.3 `repair_evaluate` 报修评价信息表

| 字段 | 含义/作用 |
|---|---|
| `repair_id` | 关联 `repair.id`，表示评价针对的报修单 |
| `owner_id` | 关联 `owner.id`，表示发起评价的业主 |
| `score` | 总体评分（1-5分） |
| `evaluate_content` | 评价文字内容 |
| `evaluate_images` | 评价时上传的图片，多张以逗号分隔 |
| `service_attitude` | 服务态度细分评分（1-5分） |
| `repair_quality` | 维修质量细分评分（1-5分） |
| `response_speed` | 响应速度细分评分（1-5分） |

细分评分用于更精细地考核维修人员/物业的服务水平。

### 3.4 `complaint` 投诉建议信息表

| 字段 | 含义/作用 |
|---|---|
| `complaint_no` | 投诉/建议编号，全局唯一，便于跟踪 |
| `owner_id` | 关联 `owner.id`，表示发起人 |
| `complaint_type` | 类型：1=投诉、2=建议，区分负面反馈和正向建议 |
| `complaint_category` | 具体分类（物业服务/环境卫生/安全隐患/设施损坏/其他），便于统计分析高频问题 |
| `complaint_title` | 标题，列表页展示用 |
| `complaint_content` | 详细内容描述 |
| `complaint_images` | 佐证图片，多张以逗号分隔 |
| `contact_phone` | 联系电话 |
| `handle_user_id` | 关联 `sys_user_info.id`，表示负责处理此投诉/建议的客服或管理人员 |
| `handle_time` | 处理完成的时间 |
| `handle_result` | 处理结果说明 |
| `status` | 状态：0待处理→1处理中→2已处理→3已关闭 |
| `satisfaction` | 业主对处理结果的满意度评分（1-5分） |

### 3.5 `inspection` 巡检信息表

| 字段 | 含义/作用 |
|---|---|
| `inspection_no` | 巡检任务编号，全局唯一 |
| `inspection_name` | 巡检任务名称（如"2月消防设施巡检"） |
| `community_id` | 关联 `community.id`，表示巡检所属小区 |
| `inspection_area` | 巡检覆盖的具体区域（如"1号楼、2号楼"） |
| `inspector_id` | 关联 `sys_user_info.id`，表示执行巡检的人员 |
| `plan_start_time` / `plan_end_time` | 计划开始/结束时间，用于任务排期 |
| `actual_start_time` / `actual_end_time` | 实际开始/结束时间，用于对比计划完成情况 |
| `inspection_items` | 本次巡检需要检查的项目清单（如消防设施/电梯/楼道/停车场） |
| `status` | 状态：0待执行→1巡检中→2已完成→3已取消 |

### 3.6 `inspection_record` 巡检整改信息表

| 字段 | 含义/作用 |
|---|---|
| `inspection_id` | 关联 `inspection.id`，表示该问题来自哪次巡检任务 |

## 四、财务管理模块

> "账单查询"不新增数据表，而是基于 `bill` 与 `payment_record` 联合查询实现（如按业主/房屋/状态/账期筛选），故本模块只设计 3 张表。

### 4.1 `fee_item` 费用项目信息表

| 字段 | 含义/作用 |
|---|---|
| `fee_code` | 费用编码，唯一标识一种费用项目（如 `FEE_PROPERTY`） |
| `fee_name` | 费用名称，界面展示用（如"物业费""停车费"） |
| `fee_type` | 费用大类：1物业费、2水费、3电费、4停车费、5其他，便于统计分类 |
| `charge_mode` | 计费方式：1按面积计费（金额=单价×房屋面积）、2固定金额（如车位月租）、3按用量计费（如水表读数×单价） |
| `unit_price` | 单价，具体含义随 `charge_mode` 变化（元/㎡、元/车位、元/吨等） |
| `unit` | 计价单位说明文字，便于界面展示价目表 |
| `billing_cycle` | 计费周期：1月度、2季度、3年度、4一次性，决定账单生成的频率 |
| `status` | 状态：1启用、0停用（停用后不再用于生成新账单，但历史账单不受影响） |

### 4.2 `bill` 账单信息表

| 字段 | 含义/作用 |
|---|---|
| `bill_no` | 账单编号，全局唯一，供业主对账、系统追溯使用 |
| `house_id` | 关联 `house.id`，表示该账单针对的房屋 |
| `owner_id` | 关联 `owner.id`，表示该账单的缴费责任人 |
| `fee_item_id` | 关联 `fee_item.id`，表示该账单对应的费用项目 |
| `period_start` / `period_end` | 账单覆盖的账期起止日期（如某月的物业费） |
| `amount` | 应收金额，由费用项目单价结合房屋面积/用量等计算得出 |
| `paid_amount` | 已收金额，随缴费登记逐步累加，用于判断是否欠费或部分缴纳 |
| `due_date` | 缴费截止日期，超期未缴可用于催缴或滞纳金计算（如后续扩展） |
| `generate_time` | 账单生成时间，即"账单生成"功能执行的时间戳 |
| `status` | 账单状态：0未缴纳、1部分缴纳、2已缴清、3已作废（如生成有误需要冲销） |

### 4.3 `payment_record` 缴费登记信息表

| 字段 | 含义/作用 |
|---|---|
| `payment_no` | 缴费流水号，全局唯一，作为一笔实际收款的凭证编号 |
| `bill_id` | 关联 `bill.id`，表示本次缴费针对的账单（一张账单可对应多笔缴费记录，如分期缴纳） |
| `owner_id` | 关联 `owner.id`，表示实际缴费人 |
| `pay_amount` | 本次缴费金额，累加到对应账单的 `paid_amount` |
| `pay_method` | 缴费方式：1现金、2微信、3支付宝、4银行卡、5其他，便于财务对账分渠道统计 |
| `pay_time` | 实际缴费时间 |
| `operator_id` | 关联 `sys_user_info.id`，表示登记这笔缴费的工作人员（前台收银/客服） |
| `voucher_no` | 第三方支付平台的交易流水号或纸质凭证编号，用于对账核实 |
| `status` | 状态：1有效、0已作废（登记有误被撤销后，不计入账单已收金额） |

**业务闭环**：`fee_item` 定义收费标准 → 定期批量生成 `bill`（账单生成）→ 前端/后台按条件筛选 `bill` 联合 `payment_record`（账单查询）→ 业主实际缴费后插入 `payment_record` 并累加更新对应 `bill.paid_amount` 及 `status`（缴费登记）。

## 索引/唯一约束说明

- `repair_no`、`complaint_no`、`inspection_no`、`record_no`、`fee_code`、`bill_no`、`payment_no` 均建立**唯一索引**，保证业务单号/编码不重复，方便对外查询和追溯。
- 所有外键字段（如 `community_id`、`owner_id`、`house_id`、`bill_id` 等）均建立**普通索引**，加速关联查询（JOIN）和外键校验性能。
- 所有表的 `deleted` 字段均建立**普通索引**，因为几乎每条查询语句都会带上 `deleted = 0` 条件，索引可以避免全表扫描，尤其在数据量增长后对列表查询性能提升明显。

> 注意：本项目中同名索引 `idx_deleted` 被重复用在多张表上。在 MySQL 里索引名只需要在**单表内**唯一即可，不同表可以使用相同的索引名，因此这样写不会报错；但如果后续引入数据库管理工具按索引名全局搜索/管理索引，可能不便区分。如需更严谨，可以命名为 `idx_{表名}_deleted`（如 `idx_house_deleted`）。
