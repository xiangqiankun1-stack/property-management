# 2. 技术难点与解决方案

## 2.1 Maven依赖冲突：MyBatis-Plus与PageHelper分页冲突

**问题描述**：项目中同时引入了MyBatis-Plus和PageHelper两个持久层框架。两者都提供了分页功能，但在运行时mybatis-plus的分页插件与PageHelper的拦截器产生了冲突，导致分页查询结果异常。

**解决方案**：经过分析，MyBatis-Plus自带的分页插件`PaginationInnerInterceptor`已经能够满足项目的分页需求，且功能更强大（支持多数据库类型），因此决定**移除PageHelper依赖**，统一使用MyBatis-Plus的分页机制。同时自定义了通用的`Page<T>`类作为统一分页返回格式。

```java
// 统一分页返回格式
public class Page<T> {
    private long total;      // 总记录数
    private int pages;       // 总页数
    private int current;     // 当前页
    private int size;        // 每页大小
    private List<T> records; // 数据列表
}
```

## 2.2 前后端接口对接：登录传参方式不匹配（415错误）

**问题描述**：后端登录接口使用`@RequestParam`接收参数，期望前端以`application/x-www-form-urlencoded`格式提交。但前端Axios默认以`application/json`格式发送请求体，导致HTTP 415（Unsupported Media Type）错误。

**解决方案**：在Axios请求拦截器中，对登录接口特殊处理，动态设置`Content-Type`为`application/x-www-form-urlencoded`。对于其他接口，统一使用JSON格式。这样在不修改后端接口的前提下解决了对接问题。

```javascript
// 请求拦截器中判断登录接口
if (isLogin && !config.headers['Content-Type']) {
  config.headers['Content-Type'] = 'application/x-www-form-urlencoded'
}
```

## 2.3 JWT Token认证与跨域处理

**问题描述**：前后端分离架构下，前端（localhost:5173）与后端（localhost:8080）存在跨域问题。同时需要实现基于JWT Token的无状态认证，区分需要认证和无需认证的接口。

**解决方案**：

1. **CORS配置**：在`WebConfig`中配置全局CORS，明确允许前端域名`http://localhost:5173`的跨域请求，允许携带凭证（`allowCredentials: true`）。
2. **JWT Token认证流程**：

   - 用户登录成功后，后端生成JWT Token（有效期6天），将用户ID和用户名存入Token的Claims中
   - 前端将Token存储在localStorage中，每次请求在`Authorization`头中携带`Bearer {token}`
   - 后端`LoginInterceptor`拦截`/api/v1/**`路径，验证Token有效性，将用户信息存入ThreadLocal
   - 排除登录和注册接口的Token校验
3. **ThreadLocal上下文传递**：自定义`ThreadLocalUtil`工具类，在请求处理过程中保存和传递当前用户信息，请求结束后自动清理，防止内存泄漏。

```java
// LoginInterceptor核心逻辑
public boolean preHandle(HttpServletRequest request, ...) {
    if ("OPTIONS".equalsIgnoreCase(request.getMethod())) {
        return true; // 预检请求直接放行
    }
    String token = request.getHeader("Authorization");
    if (token != null && token.startsWith("Bearer ")) {
        token = token.substring(7);
    }
    Map<String, Object> claims = JwtUtil.parseToken(token);
    ThreadLocalUtil.set(claims);  // 存入ThreadLocal
    return true;
}
```

## 2.4 业务编号自动生成策略

**问题描述**：报修单号、投诉编号、账单编号等业务编号需要保证唯一性和可读性，且在高并发场景下要避免重复。

**解决方案**：采用 **"业务前缀 + 时间戳（精确到秒）+ 4位随机数"** 的编号生成策略。例如报修单号`BX202507071430251234`，前缀标识业务类型，时间戳保证时间维度的唯一性，随机数进一步降低碰撞概率。对于实训项目的并发量级，此方案完全满足需求。

```java
String repairNo = "BX" 
    + LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMddHHmmss"))
    + String.format("%04d", new Random().nextInt(10000));
```

## 2.5 级联删除的事务处理

**问题描述**：删除报修记录时，需要同时删除关联的派单记录（repair_order）和评价记录（repair_evaluate）；删除账单时需要同时删除关联的缴费记录（payment_record）。这些操作必须保证原子性。

**解决方案**：使用Spring的`@Transactional`注解实现声明式事务管理。在Service层方法上添加该注解，确保关联的多个删除操作要么全部成功，要么全部回滚。

```java
@Override
@Transactional
public boolean delete(Long id) {
    // 1. 删除关联的派单记录
    LambdaQueryWrapper<RepairOrder> orderWrapper = new LambdaQueryWrapper<>();
    orderWrapper.eq(RepairOrder::getRepairId, id);
    repairOrderMapper.delete(orderWrapper);
    // 2. 删除关联的评价
    LambdaQueryWrapper<RepairEvaluate> evaluateWrapper = new LambdaQueryWrapper<>();
    evaluateWrapper.eq(RepairEvaluate::getRepairId, id);
    repairEvaluateMapper.delete(evaluateWrapper);
    // 3. 删除报修记录（逻辑删除）
    return repairMapper.deleteById(id) > 0;
}
```

## 2.6 前端数据看板的图表实现

**问题描述**：数据统计看板需要展示报修趋势、投诉趋势和缴费分布等图表。由于没有专门的后端统计接口，需要基于现有CRUD接口进行数据处理和可视化。

**解决方案**：

1. **数据获取**：使用`Promise.all`并行请求多个业务接口（报修列表、投诉列表、业主列表、缴费列表），提高数据加载效率。
2. **数据降级**：当后端接口不可用时，自动降级为预设的模拟数据，保证页面正常展示。
3. **数据处理**：前端对原始数据进行分组聚合（如按月分组统计报修数量），再进行图表渲染。
4. **ECharts集成**：使用ECharts 6.0创建折线图（报修趋势）、柱状图（投诉趋势）和环形饼图（缴费分布），并通过响应式设计适配不同屏幕尺寸。

## 2.7 前端全局错误处理与Token过期处理

**问题描述**：前端需要统一处理各类HTTP错误（401未认证、404不存在、500服务器错误）和网络异常，避免每个页面重复编写错误处理逻辑。

**解决方案**：在Axios响应拦截器中实现全局错误处理：

- **401**：清除本地Token，跳转登录页
- **500**：提取后端错误信息并展示
- **404**：提示接口不存在
- **网络异常**：统一提示"网络异常"

```javascript
service.interceptors.response.use(
  (response) => { /* 正常处理 */ },
  (error) => {
    if (status === 401) {
      localStorage.removeItem('token')
      window.location.href = '/login'
    } else if (status === 500) { /* 服务器错误 */ }
    else if (status === 404) { /* 接口不存在 */ }
    else { /* 网络异常 */ }
    return Promise.reject(error)
  }
)
```

## 2.8 MyBatis-Plus自动填充与逻辑删除

**问题描述**：每张表都有`create_time`、`update_time`、`create_user`、`update_user`、`deleted`等通用字段，如果每次手动设置会导致大量重复代码。

**解决方案**：利用MyBatis-Plus的`MetaObjectHandler`自动填充机制和`@TableLogic`逻辑删除注解，实现通用字段的自动处理：

1. **自动填充**：`MyMetaObjectHandler`在插入时自动填充创建时间、更新时间、创建人、更新人；在更新时自动填充更新时间和更新人。
2. **逻辑删除**：`BaseEntity`中使用`@TableLogic`注解标记`deleted`字段，删除操作自动转换为`UPDATE SET deleted=1`，查询自动添加`WHERE deleted=0`条件。

```java
@Component
public class MyMetaObjectHandler implements MetaObjectHandler {
    public void insertFill(MetaObject metaObject) {
        this.strictInsertFill(metaObject, "createTime", LocalDateTime.class, LocalDateTime.now());
        this.strictInsertFill(metaObject, "deleted", Integer.class, 0);
    }
}
```

通过本项目完整的开发实践，深刻理解了前后端分离架构的工作模式：后端专注提供RESTful API接口，前端负责页面渲染和用户交互，两者通过HTTP协议和JSON数据格式进行通信。这种架构使得前后端可以并行开发，提高开发效率。

### Spring Boot生态的实践经验

- 掌握了Spring Boot项目的标准开发流程：Controller → Service → Mapper三层架构
- 熟练运用MyBatis-Plus进行数据访问，包括自动填充、逻辑删除、Lambda查询包装器等高级特性

# 5. 不足与改进方向

## 5.1 技术层面

### 后端方面

| 不足                                                                                                                                            | 改进方向                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **缺少全局异常处理**：当前各Controller方法中通过if-else判断返回成功/失败，未使用`@RestControllerAdvice`全局异常处理器，异常处理逻辑分散 | 引入全局异常处理机制，自定义业务异常类，统一异常返回格式，使Controller代码更简洁 |
| **密码存储使用MD5而非BCrypt**：MD5已被证明不够安全，容易被彩虹表破解                                                                      | 改用Spring Security的BCryptPasswordEncoder或更安全的哈希算法（如bcrypt、argon2） |
| **缺少参数校验**：虽然使用了`@Validated`注解，但部分校验逻辑不够完善                                                                    | 完善Bean Validation注解使用，添加自定义校验器，增强输入安全性                    |
| **日志体系不完善**：未引入日志框架（如Logback/SLF4J），调试依赖System.out                                                                 | 引入SLF4J + Logback日志框架，按级别记录日志，便于问题排查和系统监控              |
| **缺少API文档自动生成**：API文档为手写Markdown，与代码不同步                                                                              | 集成Knife4j/Swagger，实现API文档自动生成，确保文档与代码一致                     |
| **未使用DTO进行数据隔离**：部分接口直接暴露Entity对象，存在数据安全隐患                                                                   | 引入VO/DTO分层，前端请求使用DTO接收，响应使用VO返回，隔离内部数据结构            |
| **分页功能未充分利用**：部分查询接口返回全量数据，数据量大时影响性能                                                                      | 统一使用MyBatis-Plus分页插件，所有列表接口支持分页查询                           |
| **JWT密钥硬编码**：JWT签名密钥"smart"直接写在代码中，安全性不足                                                                           | 将密钥移至配置文件，使用环境变量管理敏感信息                                     |

### 前端方面

| 不足                                                                 | 改进方向                                            |
| -------------------------------------------------------------------- | --------------------------------------------------- |
| **未使用TypeScript**：项目使用纯JavaScript开发，缺少类型检查   | 引入TypeScript，提高代码可维护性和开发体验          |
| **组件复用度可进一步提升**：各页面仍有重复的CRUD逻辑           | 抽离通用CRUD Hook（useCrud），减少模板代码          |
| **缺少单元测试**：前端未编写任何自动化测试                     | 引入Vitest进行组件和工具函数单元测试                |
| **权限控制仅前端路由拦截**：未实现按钮级别的权限控制           | 结合后端权限数据，实现按钮级和API级的细粒度权限控制 |
| **数据看板数据依赖实际业务数据**：统计图表需要真实数据才有意义 | 开发后端统计聚合接口，提供专门的统计数据API         |

### 数据库方面

| 不足               | 改进方向                       |
| ------------------ | ------------------------------ |
| 部分表缺少外键约束 | 补充外键约束，保证数据一致性   |
| 缺少数据库备份策略 | 制定定期备份方案               |
| 索引覆盖不够全面   | 根据实际查询场景分析并补充索引 |

## 5.2 项目管理层面

| 不足                                                                                   | 改进方向                                                                       |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **Git分支管理不规范**：所有人直接在master分支上开发，缺少feature分支和PR审查流程 | 采用Git Flow或GitHub Flow工作流，使用feature分支开发，通过PR进行代码审查后合并 |
| **缺少持续集成**：每次提交后需手动测试，效率不高                                 | 配置CI/CD流水线，自动构建、自动测试                                            |
| **需求变更未文档化**：开发过程中需求调整未及时更新文档                           | 建立需求变更记录机制，确保文档与实现一致                                       |
| **测试覆盖不够深入**：主要进行了功能测试，缺少性能和压力测试                     | 增加性能测试、压力测试和安全性测试                                             |
| **进度跟踪不够透明**：缺少每日站会和进度看板                                     | 使用项目管理工具（如TAPD、Trello）进行任务跟踪                                 |

## 5.3 功能完善方向

1. **业主端移动适配**：当前系统主要面向PC端管理后台，可增加移动端适配或小程序端，方便业主使用
2. **消息通知机制**：增加站内消息或短信通知功能，报修状态变更、缴费提醒等可实时通知业主
3. **数据导入导出**：支持Excel批量导入导出基础数据，提高数据维护效率
4. **操作日志审计**：记录关键操作日志，便于追溯和审计
5. **图像上传功能**：报修时可上传现场照片，方便维修人员了解情况
